## 卡在哪
- `python -m app.rag.graph` 第一条查询正常出结果，第二条在 `generate` 节点崩：
  `RuntimeError: Event loop is closed`（traceback 落在 `llm.ainvoke` 之后、连接池关闭阶段）。
  同一条命令里前一条成功、后一条崩，说明不是 key、不是网络、也不是 DeepSeek 侧的问题。

## 为什么
- `asyncio.run(...)` 被写进了 `for q in QUERIES` 循环体：每轮都新建并关闭一个事件循环。
- 而模块级 `llm` 里的 httpx 异步连接池在第一次调用时就绑在了第一个 loop 上；
  第二轮结束时它去关闭一条属于已关闭 loop 的传输 → `call_soon` 失败。
- 这是「`async def` 一出现，调用方式就得跟着改」的第二次翻车（S1 那次是 `invoke` / `ainvoke`）。

## 怎么解
- 三条查询收进一个 `async def _main()`，用 `await` 串起来，入口只调一次 `asyncio.run(_main())`；重跑三条全过。
- 规则记下来：异步客户端不能跨事件循环复用；入口统一 `ainvoke`，一个进程一个 loop。

## 附记（不是卡点）
- 同一查询（`设备离线了怎么处理?`）、同一份候选、`temperature=0`，两次运行答案不同：
  一次按设备分述、一次整体拒答 → SYSTEM 里「材料中没有就直接拒答」约束过硬。
  补一句「若材料按不同设备/型号分别给出答案，就分别列出，不要因为问题宽泛而整体拒答」后，
  **连跑两轮都稳定分述**。结论：prompt 改动要按「连跑两次一致」验收，一次对不算。
- 一度据第一问四候选挤在 0.988–0.994 判断「阈值不可用」，实测负样本 0.0199 推翻 ——
  错在比较对象：同一条查询内部候选之间的间距，和跨查询之间的量级，不是一回事。
- `RERANK=kw` 的分数是 bigram 重叠率（另一套尺度），因此**不受** `MIN_RERANK` 约束；
  README 要写清这个不对称，否则被问「阈值怎么定的」会讲不圆。
- 加阈值后负样本不再进 LLM，`RUN_LLM=1` 那条测试证的是「行为断言成立」；
